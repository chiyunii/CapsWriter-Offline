# CapsWriter-Offline 服务端可观测性与持久化功能

> 本文档描述为 CapsWriter-Offline 服务端新增的两个功能：**运行时指标监控（可观测性）** 与 **识别结果持久化与检索**。两个功能均为纯 Python 标准库实现，零第三方依赖，可独立运行与测试。

---

## 一、功能总览

| 功能 | 新增/改动模块 | 核心能力 |
|------|--------------|---------|
| 可观测性 | `core/server/metrics.py`、`core/server/http_api.py` | 线程安全指标采集（counter/gauge/histogram）、Prometheus 格式导出、HTTP 健康检查 |
| 持久化与检索 | `core/server/storage.py`、`core/server/http_api.py` | SQLite WAL 存储、FTS5 全文检索、多条件查询与统计 |

**集成改动**：

- `config_server.py`：新增 HTTP 接口与数据库路径配置项
- `core/server/app.py`：装配三个组件并管理其生命周期
- `core/server/connection/ws_recv.py`：连接建立/断开埋点
- `core/server/connection/ws_send.py`：任务/耗时/RTF 埋点 + 最终结果持久化

## 二、功能 1：运行时指标监控（可观测性）

### 2.1 指标模型

`MetricsRegistry` 提供三类线程安全指标：

| 类型 | 语义 | 典型指标 |
|------|------|---------|
| counter | 单调递增累计值 | 连接总数、任务总数、错误总数 |
| gauge | 可增可减瞬时值 | 活跃连接数、队列长度、RTF |
| histogram | 数值分布 | 识别耗时（含分桶） |

采集的指标清单（Prometheus 命名）：

| 指标名 | 类型 | 含义 |
|--------|------|------|
| `caps_server_uptime_seconds` | gauge | 服务运行时长 |
| `caps_server_connections_total` | counter | 累计连接数 |
| `caps_server_connections_active` | gauge | 活跃连接数 |
| `caps_server_tasks_total{type}` | counter | 累计任务数（按 mic/file 分标签） |
| `caps_server_queue_length` | gauge | 输入队列积压 |
| `caps_server_recognition_duration_seconds` | histogram | 识别耗时分布 |
| `caps_server_rtf{type}` | gauge | 实时率（处理耗时 / 音频时长） |
| `caps_server_errors_total` | counter | 错误累计 |

### 2.2 设计要点

1. **线程安全**：WebSocket 收发与 HTTP 服务分属不同线程，所有读写通过内部锁保护。
2. **主进程聚合**：识别耗时通过 `Result` 中的 `time_submit` / `time_complete` 时间戳在主进程侧计算，避免在识别子进程与主进程间引入额外共享内存结构。
3. **零依赖 HTTP**：基于 `http.server.ThreadingHTTPServer` 实现，独立守护线程运行，不阻塞主进程的 WebSocket 事件循环。

## 三、功能 2：识别结果持久化与检索

### 3.1 数据模型

`records` 表存储每条完成识别的结果：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增主键 |
| task_id | TEXT | 任务唯一标识 |
| source | TEXT | 来源（mic / file） |
| text / text_accu | TEXT | 主要输出 / 精确输出 |
| duration | REAL | 音频时长（秒） |
| tokens / timestamps | TEXT(JSON) | 字级 token 与时间戳 |
| time_start / submit / complete | REAL | 任务时间戳 |
| created_at | TEXT | 入库时间（ISO 8601） |

### 3.2 设计要点

1. **WAL 模式**：启用 Write-Ahead Logging，读写互不阻塞，提升并发吞吐。
2. **全文检索**：优先使用 FTS5 `trigram` 分词器（对中文子串匹配友好）；关键词不足 3 字符或环境不支持 FTS5 时自动降级为 `LIKE`，保证正确性。
3. **索引设计**：为 `task_id`、`source`、`created_at` 建立索引，加速过滤与排序。
4. **参数化查询**：所有 SQL 使用占位符绑定，杜绝 SQL 注入。

## 四、HTTP 接口说明

服务启动后默认监听 `127.0.0.1:6017`（可通过 `config_server.py` 的 `http_api_host` / `http_api_port` 修改，`enable_http_api=False` 可关闭）。

| 接口 | 方法 | 说明 | 参数 |
|------|------|------|------|
| `/health` | GET | 健康检查（JSON） | - |
| `/metrics` | GET | Prometheus 文本格式指标 | - |
| `/records` | GET | 识别结果检索（JSON） | `keyword` / `source` / `limit` / `offset` |
| `/records/stats` | GET | 存储概况统计（JSON） | - |

### 4.1 示例：健康检查

```
GET /health
→ {"status": "ok", "version": "2.6", "uptime_seconds": 0.304, "connections_active": 1}
```

### 4.2 示例：指标（节选）

```
# TYPE caps_server_tasks_total counter
caps_server_tasks_total{type="file"} 1
caps_server_tasks_total{type="mic"} 1
# TYPE caps_server_recognition_duration_seconds histogram
caps_server_recognition_duration_seconds_count 2
caps_server_recognition_duration_seconds_sum 0.57
caps_server_recognition_duration_seconds_bucket{le="0.5"} 2
```

### 4.3 示例：检索

```
GET /records?keyword=天气
→ {"total": 1, "items": [{"text": "今天天气不错，我们出去走走吧", ...}]}
```

## 七、面试可追问点（提前准备）

1. **为什么选择标准库 HTTP 而不是引入 FastAPI/Flask？** —— 项目定位是零依赖离线工具，标准库即可满足监控接口需求，减少打包体积与依赖冲突。
2. **FTS5 trigram 的局限？** —— trigram 要求查询词 ≥ 3 字符，短关键词（1~2 字）无法命中，因此设计了按长度自动降级 LIKE 的策略。
3. **WAL 模式解决了什么问题？** —— 默认回滚日志模式下读写互斥，WAL 允许读不阻塞写、写不阻塞读，提升 WebSocket 写入与 HTTP 查询并发。
4. **指标为什么在主进程聚合？** —— 识别耗时通过结果消息携带的时间戳计算，避免跨进程共享内存（`multiprocessing.Manager` 的锁与序列化开销）。
5. **SQL 注入如何防范？** —— 全部使用参数化占位符，且 FTS5 查询词做了字符白名单校验。
